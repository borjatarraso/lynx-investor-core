# i18n

The runtime ships two parallel translation stacks. They exist for
different reasons and are not interchangeable; read this before
touching either.

## Why two

- **`i18n` (gettext)** is a thin wrapper over the stdlib
  `gettext`. It was the first stack introduced and is what
  `lynx_investor_core.cli` and the older parts of every consuming
  agent use. Catalogues are real `.po` / `.mo` files.
- **`translations` (JSON pool)** is a small dict-based store added
  later for the GUI and TUI label paths, where a flat key → string
  lookup is much faster to author and to live-reload than a gettext
  catalogue. It also drives the `--language=…` CLI flag that
  consuming agents wire up to `add_language_argument()`.

Collapsing one onto the other is on `ROADMAP.md`, but only after
every consumer has migrated off the gettext entry points.

## `i18n` (gettext)

```python
from lynx_investor_core.i18n import _, set_locale

set_locale("es")
print(_("Positions"))           # → "Posiciones" once compiled
```

Catalogues live at:

```
lynx_investor_core/locales/<code>/LC_MESSAGES/lynx.{po,mo}
```

A locale request for which no `.mo` exists falls back silently to
`gettext.NullTranslations` (identity). The environment variable
`LYNX_LOCALE` is honoured at import time, so:

```sh
LYNX_LOCALE=es lynx-portfolio -p -i
```

…installs the catalogue before any user-visible output.

`cli.apply_locale()` is called from the agent entry point right
after `parse_args` to override the env-var default with the
`--locale` flag. Passing `--locale=""` or `--locale=none` reverts
to source-language English even if `LYNX_LOCALE` is set.

## `translations` (JSON pool)

```python
from lynx_investor_core import translations as tr

tr.set_language("es")
print(tr.t("nav.dashboard"))    # → "Panel"
```

Two pools:

```
lynx_investor_core/locales/core/<lang>.json          # UI labels
lynx_investor_core/locales/extensive/<lang>.json     # long-form copy
```

Supported codes: `us` (English, default), `es`, `it`, `de`, `fr`,
`fa` (Farsi). Codes are case-insensitive on input.

Keys are stable identifiers (`nav.dashboard`, `buttons.refresh`) —
not English text. Missing keys in any language fall back to `us`
silently.

The chosen language persists to:

```
$XDG_CONFIG_HOME/lynx/language.json
```

(or `~/.config/lynx/language.json`). `LYNX_LANG=es` is the env-var
override for ad-hoc shells.

## CLI flag plumbing

Every consuming agent's parser inherits both flags via the
`add_standard_args` boilerplate:

- `--locale CODE` → routed to `i18n.set_locale`.
- `--language CODE` → routed to `translations.set_language`.

The two are kept separate so the gettext catalogue and the JSON pool
can switch independently — a user who wants Spanish UI labels and
English error messages, or vice versa, is honoured.

## Adding a new language

1. Add `locales/core/<code>.json` mirroring the keys in `us.json`.
2. Optionally add `locales/extensive/<code>.json`.
3. Add a `locales/<code>/LC_MESSAGES/lynx.po`, translate, and run
   `scripts/compile_locales.py` to produce `lynx.mo`.
4. Verify with `pytest tests/test_translations.py` and
   `tests/test_i18n.py`.

`pyproject.toml`'s `package-data` glob already includes all three
file types under `locales/`; nothing else needs to change.

## Adding a new translation key

For UI labels:

1. Add the key to `locales/core/us.json` first — that is the source
   of truth.
2. Other languages may lag. The test suite intentionally does not
   require parity; missing keys fall back to `us`.

For long-form copy (descriptions, multi-sentence help text), add to
`locales/extensive/us.json` instead.
